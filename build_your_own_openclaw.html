Build Your Own OpenClaw

Build a personal AI agent from scratch over four weeks — two live sessions a week, Tuesdays and Thursdays.

By the end of four weeks, you'll have a running personal AI agent: it answers messages, remembers facts about you across conversations, executes bash commands and web searches inside an isolated Docker container, and receives messages over CLI, Telegram, and WhatsApp. Every layer — the message bus, the container runtime, the memory system, the channel adapters — is code you wrote. Along the way you'll go deep on the four pillars that make an agent production-shaped: databases as IPC, agent loops, memory & context engineering, and security & token cost management.

System Architecture

Four zones, one data path. A message enters through a channel, the host router writes it into that session's inbound.db, the container's poll loop picks it up and hands it to the Claude Agent SDK, and the reply goes back out through outbound.db to the delivery poller. No sockets between host and container — just two SQLite files and a 500 ms poll.

Weeks

01

The Message Bus & DBMS Foundations

Exit artifact: Type a message → "Echo: <your message>" appears within 1 second.

No AI yet — just the wiring that makes everything else possible, plus the database theory behind it. Build the SQLite schema that lets the host and agent container communicate without any IPC: two databases per session (inbound.db owned by the host, outbound.db owned by the container), with an even/odd sequence number split that prevents write collisions. Build the router that maps an inbound message to the right session, and the delivery poller that watches outbound and surfaces replies. Prove it works with a mock echo agent. On top of the message bus, go deep on DBMS fundamentals — transactions, isolation levels, indexing, and why SQLite's single-writer model shapes this entire architecture.

02

The Agent Container & Agent Loops

Exit artifact: Ask Claude a question in your terminal → real answer appears in 10–20 seconds.

Replace the mock with a real Dockerised Claude. Write a Dockerfile that installs Bun, tini (for clean SIGTERM propagation), and the Claude Agent SDK. Write the poll loop that runs inside the container: it watches inbound.db, calls Claude with full tool use (Bash, WebSearch, Read/Write files), and writes replies to outbound.db. Pass the API key via stdin — not env vars — so it never appears in docker inspect. Wire the host to spawn and track containers. This week also covers agent loops in depth: the plan → act → observe cycle, tool-call dispatch, and how the SDK decides when a turn is actually done.

03

Memory, Workspace & Context Engineering

Exit artifact: Tell the agent a preference → restart → it remembers without being reminded.

Give the agent a personality and a memory that outlasts sessions. Build a CLAUDE.md composition system: each agent group has a local personality file that @-imports a shared global file. Before spawning a container, compose and write the result into the session workspace — the Claude Agent SDK reads it automatically. Add a human-readable conversation log. Build an MCP server that runs inside the container and exposes two tools: write_memory (agent appends facts to its own CLAUDE.md) and send_message (agent delivers a message mid-turn, before the full response is ready). Go deeper into context engineering: what to keep in-context vs. externalize to memory, and how context compaction works as conversations grow long.

04

Connections, Security & Token Cost Management

Exit artifact: Message your agent on Telegram or WhatsApp; say "remind me in 2 minutes to check email" → reminder arrives.

Make the agent reachable from anywhere, and capable of reaching you — and lock it down. Replace the readline CLI with a Unix-socket adapter so you can connect from a separate terminal (pnpm chat) without blocking the host process. Add a Telegram adapter (long-polling — no public URL needed) and a WhatsApp adapter (via Baileys) so your agent lives in your phone. Add a schedule_task MCP tool: scheduling is just a future DB row with a process_after timestamp — the same pipeline handles it. A 60-second host scheduler wakes the container when rows come due. This week closes with security — container isolation boundaries, secret handling, and what an agent should never be allowed to touch — and token cost management: budgeting, monitoring, and controlling spend on a long-running agent.

How This Relates to the Real OpenClaw

This course builds nanoclaw — a deliberately lightweight reimplementation of OpenClaw's core idea: one personal AI agent you reach from any messaging app. The real OpenClaw is a ~500k-line system whose agents share a single Node process behind application-level permission checks. nanoclaw trades that for an architecture you can hold in your head — and a stronger security model: every agent runs in its own Docker container with OS-level isolation, not just a permission allowlist. You are not cloning OpenClaw's internals; you are rebuilding its capabilities the way you would actually want to run them on your own hardware. Each week ends with an "In real OpenClaw" note mapping what you built to its production counterpart.
